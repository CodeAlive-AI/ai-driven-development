## FPF.Reference:3 - Why FPF Exists

Project reasoning can drift when an expression or result is given a meaning or use that its basis does not support.

Without the necessary basis, a sketch may be treated as a promise, a dashboard as evidence, a model output as permission, a selected set as a single winner, a method description as performed work, a diagram as architecture, a safety case as safety, or a metaphor as an ontology. Familiar wording then hides a change in what the project claims or does.

FPF addresses that drift while preserving useful early inquiry and communication. Early recognition can use provisional language. When the language supports a consequential claim or action, recover its meaning, applicable conditions and support. Use the defining or constraining pattern when a kind, predicate or support requirement is unresolved; add formal notation or an exact `ClaimGraph` locator only when the use needs it.

The practical ambition is simple: keep difficult reasoning alive long enough to improve it. A project should be able to generate alternatives, preserve uncertainty, compare options, choose locally, publish decisions, reopen stale claims, and repair language without losing the EntityOfConcern the reasoning was about.

For humans, FPF gives a shared working memory for complex reasoning. For AI agents, FPF gives typed constraints, named distinctions, and checkable written forms so generated text can be checked against the work and results it describes. For organizations, FPF gives a way to make reasoning transfer across teams without pretending that all teams use the same local meanings.
