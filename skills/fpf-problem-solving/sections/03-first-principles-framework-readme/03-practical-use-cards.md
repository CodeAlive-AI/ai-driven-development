## Practical-Use Cards

Start with the current project question, not an ordinal route through FPF. The sixteen semantic keys below are stable navigation identifiers, not steps, kinds, relations, records, or result names. When several cards seem plausible, compare their situations, first-result differences, and stop or return conditions in the conversation. Then inspect the direct pattern's Problem frame, Problem, Forces, Solution, Consequences, and ordinary boundary. Materialize comparison or candidate records only when a named receiving use relies on them.

In each card, the conditional template list is one ordinary walkthrough: inspect only the branch whose stated condition is current and then open that direct pattern's `Solution`. A branch is a context-free promise of what a later use could return, or an honest stop; it does not say that a project result already exists. The sixteen alternatives are not asserted as typed positions in one admitted constraint-governed structure, and the README asserts no relations among all of them. The list is therefore not a `DemonstrativeUnfoldingSlice@Context`, a project order, or a claim that all branches will execute.

For the selected branch, first answer three plain questions. What useful result or honest stop can the selected card offer now? What current project question or action would that answer? Which fact or rule is still missing? The result must still match the selected `Solution`; a document label or familiar phrase does not make it truthful. If that answer is sufficient and no downstream identity or reliance is current, stop there. Only when the result's kind, identity, obtaining, application, or reliance changes the claim should you recover the exact definition, membership test, or obtaining predicate; name the relevant Method, plan, dated `U.Work`, transformation, evaluation, decision, publication, or reliance use; and cite the relation occurrence, A.6.1 application binding, or supported local claim that makes the result usable there. Cite another pattern only when its concrete contribution changes the continuation.

The cards are domain-neutral. A first useful result may be a physical or clinical state, a capability, an episteme, a relation, dated `U.Work`, or another exact project value. A generated note, measurement, dashboard, or plan does not stand for machining, treatment, organizational change, learning, or another downstream result.

#### Four direct starts when a familiar phrase hides the object

These are four independent disambiguation routes before card-key comparison, not extra cards or steps. Use only the route matching the current sentence; each one returns a direct-pattern result or an exact blocker, then stops.

- **“We need to refer to the relation that actually holds.”** Name the exact participants and direct relation, then open the pattern that owns it. A readable assertion is the smallest result when later work only needs to know that it obtains. Use `A.6.REL` only when history, comparison, another relation, or an operation application must distinguish one occurrence from another; apply the direct identity rule before naming or referencing it. Stop when the receiving use can use the assertion or individuated occurrence. If a participant, current fact, predicate, identity rule, or direct governor is missing, return that exact blocker. If exact recovery finds no current direct relation for the claim, exit to `A.6.RCD`; a row, edge, label, file, report, or identifier creates no occurrence.
- **“Project, process, or case wording hides what this decision is about.”** Open `A.15.6`. Recover an actual project as qualifying composite `U.Work`; a process concern as one `U.Method`, exact A.22-selected `U.Structure`, or `TransformationFlowStructure`; or a case as one affected referent or claim plus only the governed change history and closure basis needed now, with one later use kept outside the closed case. The smallest result is that direct subject and bounded claim, or the exact missing basis. Stop when they answer the decision. If systemhood of the recovered entity still matters, exit to `A.1.SCR`. Treat *target system* as an ordinary cue for the exact project system-of-interest question. Keep intended systems, plan or decision designation, actual work-to-system facts, role interpretation, and role assignment separate; a project suffix, plan, team, dashboard, or case file identifies none of them.
- **“A bounded context was named or drawn, but its model-use organization is unclear.”** Open `A.1.1`. Recover the exact model edition, use locus, and smallest direct applicability, assigned-Work use, or coherence relation first. Select optional `BoundedModelUseStructure` under `A.22` only when the joint organization changes the decision and exact constituents, obtaining relations, applied constraints, and one selection-use frame are present. Stop at that relation or structure; otherwise return the exact missing discriminator. It is not a holon, subsystem, team, label, scheme, scope, viewpoint, view, representation, or diagram. `Context Mapping` is a `U.Method` and a cross-context organization needs its own selection. If the question is whether an episteme conforms to a viewpoint, exit to `E.17.0`.
- **“We have problem-side material, but may not have an actual problem.”** Open `C.22.PFR` only for an obtaining `ProblematicForRelation`: one exact actual-condition occurrence plus one exact criterion-applicability occurrence whose selected input is actually adverse for the named entity and use. The predicate, applicability occurrence, assessment, assertion or reliance, `ProblemCard`, modal concern, and solvability or continuation claim stay separate. Stop with the ordinary actual-problem sentence or the exact missing condition, applicability, adverse input, or governor. If the need is a reviewable problem-side formulation, exit to `C.22.2`. One card may describe no actual PFR; selecting a method changes current solvability or continuation, not PFR participants, obtaining, identity, or the adverse condition.
